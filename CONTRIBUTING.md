# Contributing to sluice

`sluice` reconciles a human-reviewed HCL manifest of approved Terraform
providers against an S3-backed network mirror. Because merging a change here
decides what provider code the fleet is allowed to execute, changes are held to
a security-review bar: every dependency, every verification path, and every
publish ordering guarantee matters.

This document covers how to report issues, propose changes, and submit pull
requests.

## Quick start

```bash
mise install   # Go, just, golangci-lint, and the rest of the pinned toolchain
just           # list every recipe
just build     # binary at build/bin/sluice
just check     # lint + test — run before pushing
```

`just --list` enumerates every recipe.

## Reporting issues

Use [GitHub Issues](https://github.com/donaldgifford/sluice/issues) for:

- **Bug reports** — include the version and commit `sluice` printed on startup,
  the exact command you ran, the relevant HCL (redact bucket names if needed),
  and what you expected versus what happened. For `apply` failures, include the
  structured log line for the affected provider/version/platform.
- **Feature requests** — describe the problem you are trying to solve, not just
  the solution you have in mind.
- **Verification or supply-chain concerns** — anything where `sluice` could
  publish an artifact it should have rejected. Treat these as security issues,
  not ordinary bugs.

For larger proposals, open a document with `docz create rfc` (or `design`) under
`docs/` and link it from the issue.

## Development setup

### Prerequisites

- [mise](https://mise.jdx.dev) — installs and pins the entire toolchain from
  `mise.toml`. You do not need a system Go.
- `git`

```bash
git clone https://github.com/donaldgifford/sluice.git
cd sluice
mise install
just check
```

The Go version is pinned in two places that must stay in sync: the `go`
directive in `go.mod` and `go = "..."` in `mise.toml`. Bump them in the same
commit.

## Making changes

### 1. Create a branch

Branch names follow `<type>/<short-description>`:

```bash
git checkout -b feature/plan-detailed-exitcode
git checkout -b fix/index-conditional-write
git checkout -b docs/yank-runbook
```

Branch prefixes `feature/`, `fix/`, `chore/`, `docs/`, and `security/`
automatically apply the matching label via `.github/labeler.yml`.

### 2. Write the code

Conventions live in `CLAUDE.md`; the ones that come up in review most often:

- **Errors wrap with `%w`** and carry the `(provider, version, platform)` tuple
  they failed on. Handle with `errors.Is` / `errors.As` at the top of the stack.
- **`slog` for structured logs.** Every publish and retract emits one structured
  line — that is the ingest audit trail, not debug output.
- **No `init()` for behavior.** Wire dependencies in `main()`.
- **Library code goes in `internal/`.** Keep `cmd/sluice/` thin.
- **Tests live next to the code.** The diff engine is pure, so test it
  table-driven. Registry and S3 sit behind small interfaces so `httptest` fakes
  and LocalStack cover them.
- **Verification must fail closed.** Any change to signature, checksum, or `h1:`
  handling needs a tampered-fixture test proving it rejects bad input.
- **Integration tests** go behind `//go:build integration` and run with
  `just test-integration`.

Every `.go` file starts with the SPDX license header, separated from the package
clause by a blank line:

```go
// SPDX-License-Identifier: Apache-2.0
// Copyright 2026 Donald Gifford

package mirror
```

The blank line matters: without it the header becomes the package doc comment.
Package documentation belongs in a `doc.go`. `golangci-lint` enforces the header
via `goheader`.

Packages under `internal/` must hold at least 60% statement coverage
(`just coverage-gate`).

### 3. Commit

Follow [Conventional Commits](https://www.conventionalcommits.org/) — commit
messages are the source of the generated changelog:

```text
feat(plan): add -detailed-exitcode
fix(publish): write index.json last when retrying a failed apply
docs(spec): clarify the yank runbook
test(mirror): cover the platform-add diff case
```

Format:

```text
<type>(<scope>): <imperative subject>

<optional body explaining why, not what>
```

Types: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `perf`, `style`,
`ci`, `build`.

### 4. Regenerate the changelog

`CHANGELOG.md` is generated by [git-cliff](https://git-cliff.org) and is **never
hand-edited**. Because your commits add an `[unreleased]` entry, the committed
file goes stale as soon as you commit — and CI fails the PR if it is:

```bash
just changelog        # regenerate CHANGELOG.md
just changelog-check  # same check CI runs
git add CHANGELOG.md
```

Never format or lint `CHANGELOG.md` by hand: prettier would reflow it and
markdownlint would flag its repeated release headings, both breaking the
byte-for-byte drift check. `.prettierignore` and `.markdownlint-cli2.yaml`
already exclude it — generated output is verified by regeneration, not linted.

### 5. Open a pull request

Push your branch and open a PR against `main`. The description should:

- Explain what changed and why
- Link the related issue with `Fixes #123` or `Refs #123`
- Include a test plan or describe how you verified the change

**Every PR needs exactly one semver label** — `major`, `minor`, `patch`, or
`dont-release`. This is enforced by the PR Label Check workflow and is not
optional: merging to `main` auto-tags a release from that label and publishes
signed, multi-arch archives. Choosing `patch` on a breaking change ships a
breaking change as a patch release.

## CI gates

Everything below must pass. `just ci` runs the same set locally.

| Workflow           | What it checks                                         |
| ------------------ | ------------------------------------------------------ |
| CI → Lint          | `golangci-lint`                                        |
| CI → Test Go       | race-detector tests, coverage floor, Codecov upload    |
| CI → Security Scan | `govulncheck` and Trivy (HIGH/CRITICAL fail the build) |
| CI → Build         | goreleaser snapshot, SBOM generation, SBOM scan        |
| CodeQL             | `security-extended` query suite                        |
| License Check      | dependency licenses against the allow list             |
| TruffleHog         | verified secret scanning                               |
| Changelog Drift    | `CHANGELOG.md` matches `git-cliff` output              |
| PR Label Check     | exactly one semver label                               |

New dependencies are reviewed on their own merits: this project's whole purpose
is controlling what third-party code enters an environment, so a dependency that
is hard to justify will be questioned. Licenses must be in the allow list in
`justfile` (`allowed_licenses`).
